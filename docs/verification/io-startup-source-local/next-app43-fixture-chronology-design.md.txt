## Recommended minimal chronology

For the normal fully executed HL IOC, use ONE logical execution transaction before sending its truthful Filled ACK:
1. Validate the actual normal action and classify rejection/lost-response fault before any executed-state mutation.
2. Allocate positive OID/TID once. Capture accepted/executed source time, actual exact quantity, price, fee/builder fee, previous signed position and raw trade identity while the synthetic venue executes the request. This happens BEFORE the first delivery delay, not by backdating a later event.
3. Update the venue's actual position once at this execution boundary. Store the terminal order with remaining0, actual full quantity and statusTimestamp=executed_ms. The raw fill's time is executed_ms, with the same OID/CLOID and frozen startPosition. Send the normal Filled aggregate ACK with actual quantity/price.
4. Preserve a finite150ms publication/delivery delay. Before publication userFills may conservatively omit this not-yet-published raw fill; orderStatus/historicalOrders can already show its truthful terminal order. At publication append the SAME immutable raw trade and broadcast the SAME event through the ordinary user wire. Do not allocate a new ID, change time, apply position again or rewrite original order execution time in the worker.
5. Broadcast a complete private clearinghouse snapshot taken at actual publication time. Its account position already includes the executed trade. Every HTTP clearinghouse and periodic private snapshot during the delay must also show the executed position; snapshot time remains its own actual collection time, independently of the trade's earlier execution time.

This describes a deliberately delayed fill-history/publication service, not proof that any actual venue uses this timing. The fixture is synthetic and the normal native client remains the only source of app events/Cache/Portfolio.

A tid counter independent of len(published_fills) is needed if raw fills can remain pending: two executions must never allocate the same tid while neither has published. Exact frozen raw rows should be private immutable execution records; returning HTTP arrays or recording evidence must not mutate their contents. Publication must be idempotent and cannot reapply position, fee or change terminal state.

Minimal source scope: hl_action classifies/executes/freezes one record; hl_fill becomes delayed publication of that record; peer gains only finite pending/next-TID evidence bookkeeping. Existing action/request/frame caps and original150ms remain. No native gate, app controller, timeout, quota or mainnet behavior changes.
