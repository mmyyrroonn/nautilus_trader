## Minimum focused additions

Reuse means using the SAME current full-account source previously verified by the normal native lifecycle, while still performing all three real empty-window reads. It must never mean an empty Cache proving account flatness. Record the captured source identity before the call and actual requests/bodies after it; source/debug flags alone do not grant authority.

## Important original-test compatibility issue

The 12 current_complete_account_mode_metadata_and_source_are_required variants change only the peer's HTTP state AFTER Harness::new has completed a valid native connect. They currently pass because startup_mass_status always refreshes the full-account HTTP group. Except wrong_metadata, which also updates ordinary Cache through a normal provider, most have no native private frame/revision invalidation at all. A new algorithm that legally reuses a sealed current source without rereading HTTP cannot observe those silent future HTTP faults.

Do not silently change their rejection expectations or claim all55 unchanged passed. Resolve the branch contract before implementation:
1. Keep the original normal full-read path exercisable by a genuine production fallback condition, not a test-only switch.
2. If modifying fixture SETUP is authorized, deliver a real invalidating private frame and prove normal receipt before mass; retain each original malformed/conflicting HTTP response and the exact old refusal/no-projection assertions. Preserve the old fixture source/hash and report why eligibility now requires fallback. Do not add a fixed sleep as receipt evidence.
3. The new reuse positive cases establish their actual sealed source before entering the three-window group. Hidden server-side changes that have neither a request nor a private signal cannot be claimed detected.
4. If the original source bytes/assertions must be entirely unchanged, production must continue actual reads for those observable fixtures or expressly not classify their normal lifecycle as reusable. This cannot be decided through harness-side Ready or opaque flags.

The existing TTL test also has a deterministic branch distinction: waiting until an old source expires before mass tests fallback; expiring DURING delayed actual windows tests final reuse refusal. Do not merge these outcomes into one forgiving assertion.

## Honest deterministic and compositional limits

- Actual identical/changed frames across history can be deterministically scheduled by awaiting a real request; receipt must be evidenced by native diagnostic/raw/current scope, not merely sending a frame. Receipt-sequence change and same-source-time financial mutation are not identical: the peer can preserve clearinghouse time while changing funds, but receipt sequence still advances. A same-received-sequence financial revision requires a different normal account callback/read race and cannot be claimed by the WS case.
- Integration cannot pause only raw ingress application, hold sibling-private native ingress/account/execution locks for a chosen duration, force same-millisecond callback internals, or mutate immutable policy without unauthorized hooks. Do not label new source/TLL tests as those exact boundaries.
- Existing websocket/client.rs unit mechanisms are prepared_private_ingress_requires_contiguous_actor_application (:2875), prepared_private_ingress_rejects_old_epoch_and_fresh_connection_markers (:2905), and prepared_private_ingress_lock_serializes_receipt_and_write_boundary (:2959). They establish unapplied/read-generation/serialization mechanics independently; a product source audit must still prove startup reuses those same guards and samples TTL after lock wait. Composition is not an actual isolated full startup integration test.
- Same-epoch new-factory behavior and queued owner cancellation have existing normal warm-query examples in io_query_recovery.rs; reuse them only if the future startup actually uses a normal owner callback. Do not invent or manually call a private startup completion executor.
- No arbitrary ticks, larger timeouts, quota changes, loop-until-pass or synthetic account/fill/cache projection. Keep original 2s account/action, 3s recovery/history and 15s app acceptance limits when following with installed-wheel application tests.
- Negative HTTP/window/policy/metadata failures stay Unknown with original raw/reader identity retained where the product supplies debt retention; reuse must not clear old source debt. Nonfresh/cold paths retain existing restrictions.
