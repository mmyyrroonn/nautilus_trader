# Independent review: sealed fresh-flat startup account proof reuse

Review date: 2026-10-09 UTC. Scope: read-only design review, not implementation acceptance. Independent product tests in this task: **0**. No Cargo, Git, GitHub, native execution/import, build, installation, source edits, environment inspection, or venue access occurred. Existing archives were not modified.

## Conclusion

A narrowly scoped reuse of an original successful full account observation is defensible **only if the observation is sealed at its original transaction boundary with the stronger source fences below**. The current trusted snapshot, current execution recovery flag, and metadata origin are insufficient to create that seal retrospectively. Reusing those existing objects directly would remove a real startup verification boundary without proving the earlier account transaction was eligible.

The proposed change can omit one repeated full-account group while preserving the three actual explicit empty-history responses and the existing fresh-flat startup contract. It must not authorize an owned-history restart, repair cold Cache adoption, clear Unknown debt, extend account validity, or manufacture a current account emission. This is a conditional design approval, not evidence of improved paired liveness. Future implementation must start from newly fetched main after PR 114 merges.

## Source findings that constrain the design

1. **The original refresh does not yet establish a reusable strong seal.** `account_scope.rs:408-478` records the full role/mode/collateral/account group, original start/source/receive, and final reader identity. Its final checks at 463-469 compare version, generation/epoch, active status and positions. They do not hold the ingress sequence fence or compare all private financial fields. `observe_ws` at 347-396 intentionally does not increment account revision for every same-position cash update or identical frame. A later startup fence cannot establish that no such frame crossed the earlier HTTP transaction. This is a prerequisite blocker for simply caching the old refresh result; it is not a request to change already submitted native113.
2. **Existing private witnesses are not the full account proof.** `PrivateFundsWitness` near 153 and its getter at 176 retain free/withdrawable and private timestamps. Balance/equity/used/cross-maintenance and complete positions require the parsed private source. `snapshot` at 282 combines old HTTP facts with the latest private receipt/source and trust checks. Neither that overlay nor serialized equality proves original HTTP provenance.
3. **A stronger pattern already exists.** `observe_account_scope` at 595 retains the bounded actual bodies, validates role/modes/collateral and source intervals; `validate_observation` at 727 compares all private financial values and positions; `commit_observation` at 781 requires the caller's original ingress fence. Warm commit in `execution_scope.rs:880-1035` composes source, token and owner checks. A startup seal should follow these actual patterns without borrowing a warm token or granting warm/cold projection authority. The raw role/mode observations and verification end are not all represented in the public account snapshot: retain their original provenance explicitly within the private sealed object.
4. **Current startup finalization is worth preserving.** `startup_mass_status` at 1496 sets one recovery deadline before any request; full-account refresh is followed by explicit frontend open-orders, user-fills and historical-orders arrays. `startup_boundary` at 1624-1774 holds ingress, account, execution guards through report construction, requires applied sequence and exact current snapshot/private funds, checks fresh journal origin and zero owned history, and compares native HTTP/Engine instruments. `execution.rs:2776` routes normal mass status here with reconciliation enabled. Reuse must retain this routing and final critical section.
5. **Metadata origin is a different authority.** `IoMetadataOrigin` near 350 and its assignment near 2540 certify selected metadata provenance; they contain neither the complete account source group nor the original account verification interval. `recover_once` at 3211 refreshes account and checks owned exposure, but its later recovery_complete flag cannot retrospectively strengthen that refresh. A valid metadata origin is necessary alongside the account seal, never a substitute for it.

## Minimum safe contract

Seal the original complete account transaction while it is still eligible, before exposing the reusable object. Capture exact client/account/address/dex/policy identity; native reader generation and epoch; received sequence and fully applied state; account and hard revisions; complete parsed private financial facts with original receipt/source; full HTTP snapshot and original start, end, account receipt/source; role, both mode brackets, collateral/native metadata and bounded raw request/response provenance. Revalidate those values under ingress -> account -> execution guards before publishing the seal. A frame arriving during the original HTTP group, including an identical or funds-only frame with unchanged general revision, prevents sealing. No retrospective reconstruction from diagnostics, public Python objects, metadata origin, or persisted account facts.

The reusable object is private, scoped to that actual runtime/client and transaction, and is not restorable from a journal or wheel ABI. Replacements, stop/disconnect, hard or financial invalidation, superseding refresh, changed account/metadata and any debt revoke eligibility. Avoid a callback/diagnostic object keeping a retired reader alive or a stale task publishing a replacement seal.

At startup entry, require the same sealed identity and original account snapshot; original start, source and receipt remain within **2 seconds**, with no future timestamp. Metadata retains its original **30-second** bound. For the smallest conservative implementation, any received-sequence change since sealing invalidates reuse even if already applied and numerically identical; do not silently rebind the old account group to a new private receipt. If that rule makes reuse rare, report that limitation rather than inventing a funds-only exemption.

Require the existing fresh locked zero-byte journal **origin**, allowing only already permitted zero-fact validation records afterward. Require zero actions/intents/fills/reservations, no source debt/taint/native projection debt, current recovery and epoch, full io empty-position account proof, and current exact selected metadata/HTTP/Engine instruments. Preserve all same-account all-strategy Cache history and account-less routed-io exclusions. Foreign or unselected financial facts are not filtered away to create flatness.

Still fetch all three complete, explicit empty arrays using the ordinary bounded transport and limiter. Missing/null/object/truncated/oversized/nonempty responses remain refusal. Receipt must belong after the original sealed observation start, with actual request/response evidence retained. Do not reinterpret absence as empty. At final owner boundary, resample time after lock waits and compare the exact seal, ingress received/applied state, account/revisions/private facts, execution/journal state, and native HTTP plus ordinary Engine Cache objects. No await between this final check and report creation.

The **3-second** recovery deadline starts once at startup entry and includes eligibility, reuse, fallback, quota, retries, arrays and final lock waits. An absent/unsealed/expired origin may take one ordinary complete refresh under that same remaining deadline, or deny startup. Fallback does not renew old timestamps, clear debt, restart the deadline, release reservations, or create an eligible origin from a failed group. Current failure remains RecoveryIncomplete/Unknown.

Reuse emits no new AccountState merely to refresh apparent freshness. Position report source time and report-window start stay tied to the original observation; report creation/receipt time can truthfully be the current local report time. Keep `set_report_window(Some(original_start), false)` and selected zero positions. Report delivery does not certify whole-account history, balances/PnL outside the scope, or generic durable Cache restoration. If a seal is intended for repeated mass-status calls, document that each call must independently perform the three arrays and pass the unchanged original TTL; reuse is not a renewable lease.

## Inventory, order and economics risks

The account and three history requests are non-atomic venue reads. Empty full arrays plus current local fences prove only the existing bounded fresh-flat startup contract; they do not guarantee that an unobserved external venue action cannot occur immediately afterward. Preserve that limitation and refuse any observed foreign/nonempty facts, including old terminal orders and fills when inventory happens to be zero. The final Cache check must cover all strategies, not just the selected strategy, and no orders may be projected or adopted during reuse.

A financial/private event invalidates the seal even if net inventory remains zero. Equity/free equality alone cannot prove absence of fills, fees, funding, transfers or an unobserved mode transition. Do not use an existing E5 attribution witness as current account authority. Existing finite economic coverage retains its exact original end; startup reuse does not extend it, record a missing fee as zero, weaken history timeout refusal, or certify run PnL. Any actual history failure still fails under the existing contract.

Current Engine Cache owner checks do not certify arbitrary post-prepare Cache mutations across the Send writer boundary. This proposal neither fixes nor expands that inherited generic limitation. Startup report consumption must still be tested through normal LiveNode/ExecutionEngine and initialized Portfolio, not by direct Cache/manual event injection.

Their rejection/error and no-financial-projection assertions remain required for the full-read path; the blanket regression statement above must not be interpreted as advertising the old 55 scenarios with identical trigger semantics.

A valid sealed proof cannot detect an unrequested hidden remote mode, role, collateral or position response. For the smallest conservative contract, keep strict equality of received sequence from seal creation through final startup commit, in addition to exact original private/account/metadata and all journal/Cache conditions. A genuine normal private frame, including an identical financial frame, invalidates reuse without inventing a revision change. In a full-read negative fixture, wait for that actual ingress and ordinary application to establish the need for refresh, then preserve the original faulty HTTP response and original rejection/no-projection assertions. Where a source is already unusable, finite refusal rather than fabricated fallback is acceptable, but separate cases must actually exercise the ordinary refresh and its refusal. Do not fake expiry, invoke a private invalidation hook, delete debt, change quota/budgets or simply allow the negative to pass.

Add separate negative cases for faulty source facts before original sealing and for actual changes crossing the reuse window. Record explicitly which old fixture preconditions changed and why; do not claim zero test-semantic changes. The wrong-metadata fixture also performs a real normal provider/Engine instrument update, which should continue to invalidate the exact object comparison independently of the remote override.

Restricting reuse to a legitimate normal-owner startup phase capability can limit repeated use or lifetime, but it cannot reveal a hidden remote change either. No harness recognition or test configuration special case is acceptable. If the intended requirement is to observe a newly changed remote mode at every startup call even without any local source invalidation, an omitted mode request cannot meet it: keep the full group, or intentionally document and test the narrower bounded original-proof contract.
