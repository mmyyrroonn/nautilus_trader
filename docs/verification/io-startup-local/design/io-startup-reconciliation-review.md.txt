# Independent design audit: bounded fresh-flat io startup reconciliation

This is a read-only design audit. Source identities/UTC are in `io-startup-reconciliation-review-sources.json`. No Git/GitHub/Cargo/build/install/product edit or new test run was performed. Implementation must start from latest main after the pending Aster dependency merges. No new issue number is assumed. Real/private venue execution remains unauthorized.

## Conclusion

A narrowly defined positive fresh-flat startup branch is feasible without generic cold-cache/owned-history reconstruction. It must construct native reports from actual current scoped reads, preserve `LiveNode(reconciliation=True)`, and refuse every non-fresh/unknown case. The existing owned recovery does not provide a native startup projection witness, so merely removing the io guards, returning None/empty mass status, or copying `recovery_complete` is incorrect.

`hyperliquid/src/execution.rs:2409/2510/2532/2569/2590` currently refuses io single-order, bulk-order, fill, position and mass-status generation. `live/src/node/mod.rs:846` normally requests each client's mass status before strategy startup and reconciles it at `:867`; thus the observed application failure occurs before entry. Application `src/entropy_execution.py:1296` keeps reconciliation enabled and disables optional periodic open/position checks. The minimal dependency can add a guarded startup-only io `generate_mass_status` path and leave general io report APIs unsupported. Later owned operations continue using the existing bounded native runtime; requests outside the new startup contract must still error.

## Positive eligibility: no historical adoption

Require the configured finite io execution policy and exact account/client/venue identity. Account-only diagnostics without execution policy must not infer the application's selected instrument universe. Require explicit genuine supported user role/account mode/DEX abstraction, USDC collateral identity and exact native metadata: unique io dex slot, active unique complete native coin, strict isolated metadata, precisions, actual repeated leverage/user-asset facts and metadata freshness. Reuse native validation rather than accepting app-provided Ready flags. Selected policy IDs must match actual loaded native instruments and settlement/precision metadata at the final boundary.

The account proof must be current, trusted and positively `flat == Some(true)` from complete explicitly io clearinghouse REST plus matching private subscription/state evidence. Null/missing/malformed `assetPositions`, absent source time, identity/scope conflict, unknown/delisted/unselected nonzero positions, negative or unrepresentable facts, or stale proof cannot mean zero. A validated complete full-scope `assetPositions: []` is a venue observation under the existing parser contract (`account_scope.rs:630-722`); merely finding no selected coin in a partial/missing list is not. If source completeness cannot be established, retain Unknown instead of generating a Flat report. Venue endpoint completeness beyond the supported local parser contract remains a protocol limitation, not an independently proved global guarantee.

Require genuinely fresh journal origin, no taint/truncation, zero prior actions, zero intents/fills, no reserved/unknown/prepared/cancel-pending facts, and `native_projection_recovery_required == false`. Read every same-account native Cache order/position across strategies including EXTERNAL, and reject existing order/fill/position history and ambiguous routed/account-less io orders. Account initialization from the scoped balance is allowed, but does not prove ownership or restoration. Do not delete/reset an old journal or adopt terminal historical facts as fresh.

Important lifecycle trap: `IoExecutionRuntime::new` reads old journal rows (`execution_scope.rs:401-444`), while normal connect already calls `runtime.recover` (`execution.rs:2323`) and successful recovery calls `persist` (`execution_scope.rs:1807`). Therefore checking current file length == 0 at mass-status time rejects even a genuinely new client. Capture a durable-origin fact when opening/locking the journal: it was actually empty before this client lifecycle. Permit only same-lifecycle internally written verification records whose action/intent/fill state remains completely empty, or restructure the fresh startup to defer/merge its first verification persist. A new client reopening any nonempty journal must refuse this fresh-only path, even when the last serialized maps are empty. Preserve normal durable history and lock semantics.

Read actual full io `frontendOpenOrders(user,dex="io")` and require a well-formed genuinely empty array; any unselected/unowned order in the io response blocks startup, even with selected zero exposure. Fresh startup cannot rely on a selected-only query hiding other io orders. Read actual retained user fills and relevant historical order sources with finite request/row/deadline bounds; missing arrays, truncation/saturated result, any io owned/unowned historical fill/order or contradictory/foreign observed activity must fail this branch. Empty history means empty supported observed window, not account-lifetime absence. Existing `observe_fill` returns early for non-io rows (`execution_scope.rs:2025`), so it is not sufficient as a foreign-fact freshness validator. Define the treatment of other-DEX history explicitly and conservatively; the minimal fresh account fixture may require the entire observed array empty. Retain rejected raw facts rather than replaying them into Cache.

## Native reports and authority boundary

Return a real `ExecutionMassStatus` with exact native client/account/venue and explicit native `PositionStatusReport(Flat, quantity=0)` for each selected verified instrument, preserving actual source timestamp where available and local receipt separately. Flat reports derive from the complete current io flat proof, not from missing rows. Empty order/fill maps require successful actual full-scope/window reads and eligible empty origin; no synthetic order/trade/commission/balance adjustment is created. Native `AccountState` continues to come from the validated scoped balance path, with exact currency projection compatibility verified rather than silently borrowing rounded positive funds.

`model/src/reports/mass_status.rs:81` defaults `reports_complete` true and its constructor has no explicit DEX/selection field. Do not accidentally claim complete venue/all-history coverage by using the default. Set/describe the report window and completeness only for the finite supported sources, and retain a native scoped startup diagnostic tying selected IDs, raw source/window coverage and source identity to the report. If the model/manager cannot distinguish a safely scoped current report from complete global reconciliation, explicitly extend that contract or keep the path blocked; do not substitute an undocumented empty report shortcut.

`live/src/execution/manager.rs:4546` reconciles venue-flat against cached netting positions; a nonzero cache can trigger synthetic adjustment rather than preserving actual source history. Fresh eligibility must reject that cache before returning reports. For a genuinely empty cache with actual Flat reports, reconciliation should produce no financial fill/position mutation. Account-qualified normal Cache plus initialized Portfolio zero is useful evidence of current local projection, not proof of durable cold restoration, run ownership or realized PnL. The application's `validate_projection` and initial-selected-flat evidence remain separate required gates before risk.

## Async/race contract

Use the existing final admission lock order (`execution_scope.rs:2373`): private ingress fence -> account state -> execution state; sample TTL only after lock waits. Carry reader generation, connection epoch, account revision, execution revision, immutable selection and exact loaded metadata identity across each async read group. Require the same reader identity and `private_ingress_guard.is_applied(epoch)` at the final report-return boundary. Generation/epoch alone misses a received but not yet actor-applied private frame. Recheck account trust/flat, journal/facts/cache freshness and metadata before publishing; no new action/prepared intent or source invalidation may intervene.

Do not hold these locks across HTTP awaits. Account refresh intentionally invalidates/increments its own revision; structure the refresh stage explicitly and then capture the revision for the open-order/history read group, or use a complete native transaction that tracks its own expected revision change. Do not accept any newly current proof to authorize old response data after reconnect/invalidation. Repeat identity/mode/open-order observations where needed within one finite deadline; a retry starts a fresh complete group, not a combination of old successes. Non-atomic REST/private observations remain documented: local fences prevent stale/mixed authority, not unobservable remote atomicity.

Existing owned recovery captures epoch/execution revision, observes real fills/status, refreshes scope, compares actual owned position and blocks `native_projection_recovery_required` (`execution_scope.rs:1636-1807`). The fresh startup branch needs the stronger reader/ingress/account-revision fence; it must not clear that cold-projection marker or release reservations. There is no need to implement full history recovery merely to start the fully fresh empty fixture, but any relaxation for old/nonempty journals, existing cached financial facts or nonzero venue positions requires that broader work first. `tests/entropy_account/execution.rs:1376` already proves a durable fill reopened with fresh Cache leaves projection recovery required and Portfolio zero; preserve that negative regression.

## Required validation before acceptance

- Positive native peer: ordinary factory/client plus genuine complete io mode/role/collateral/metadata/private evidence, fresh journal origin, actual empty full io orders/history, one and multiple selected instruments, explicit Flat reports with exact identities/source clocks, zero native synthetic financial events, Cache and Portfolio zero after normal reconciliation.
- Negative native peers: missing/null/partial positions or order/history arrays; wrong user/DEX/mode/collateral/metadata/precision; unselected io exposure/order; foreign/unknown fills or historical orders; saturated history, tainted/partial/identity-conflicting or previously nonempty journal, terminal-only old journal, unknown reservation, cached EXTERNAL/other-strategy/closed financial history, account-less routed pending order. All must retain Unknown and no entry.
- Race peers: delayed HTTP response across reader replacement, same-reader queued unapplied raw ingress, reconnect/epoch change, metadata/account/execution revision change, timestamp/TTL expiry while waiting locks, and action preparation racing report return. No partial mass status, stale reports, cached synthetic close, reservation release or post-failure resend.
- Regression: ordinary non-io report APIs/default paths remain unchanged; existing restart-no-resend/native-projection-required tests remain enforced; general io historical/single-order reconciliation remains refused when outside the bounded startup contract.
- Actual source-bound official wheel: normal installed LiveNode with both ordinary factories, reconciliation enabled, no alternate signer/executor/private HTTP/manual cache events. Start the fresh bounded synthetic loopback cycle, observe startup report consumption and initialized Cache/Portfolio, then validate the seven paired application scenarios and teardown. Before/after hash runner, peers/application source, wheel/pyd/generated stubs and provenance; retain failure output. Functional numeric loopback is not Windows kernel isolation; keep that flag false. Whole-account/funding/durable restoration/mainnet remain Unknown/unrun.

This audit proposes a contract; no implementation or future test is counted as passed. Root retains final design, review and acceptance authority.
