# Native #111 implementation handoff

The implementation is limited to normal `generate_mass_status` for an explicit io execution policy and a fresh, empty journal origin. Other io report guards and non-io report paths remain intact. Parent owns compilation, formatting, actual peer tests, review, artifacts, and merge. This implementation agent has not run Cargo, formatting, builds, ABI imports, installation, Git, or GitHub commands.

## Boundary and source contract

- `IoExecutionRuntime::new` captures `fresh_journal_origin` from the already exclusively locked journal descriptor's original byte length, before replay or persistence. A same-client empty connect record does not revoke that origin. Reopening any nonempty file cannot acquire fresh origin, including an otherwise valid empty record. Replay limits also use that locked descriptor rather than a separate pathname metadata read.
- `IoExecutionRuntime::startup_mass_status(http, emitter, core)` has one total `recovery_timeout_ms` deadline. It first validates current full io empty-position account proof, empty untainted execution facts, current recovered epoch, selected metadata, exact native instrument snapshots, and all-history Cache eligibility. It refreshes the normal account proof through the existing role/mode/collateral/full-io clearinghouse request path. Account revision changes caused by this explicit refresh are deliberate; reader generation, epoch, execution revision, metadata and instrument snapshots must remain unchanged.
- After the refresh boundary, normal `frontendOpenOrders(user, dex=io)`, unfiltered `userFills(user)`, and unfiltered `historicalOrders(user)` must each successfully return an explicit empty array. Any row is conservatively rejected, including foreign or unknown activity. Missing/null/malformed arrays fail. No old rows are filtered away to manufacture emptiness.
- `HyperliquidHttpClient::io_startup_history_body` reuses the existing native info quota/retry/transport and `economic_history_body`. Each history body is accepted only up to 1 MiB before decoding. The existing transport first buffers under its existing 100 MiB read cap. Account proof requests retain their pre-existing bounds; this change does not claim a global 1 MiB allocation cap.
- Before and after HTTP reads, all same-account orders and positions in Cache are rejected, including closed, external and cross-strategy history. Every account-less order routed to the client's venue with an io instrument namespace (selected or unselected, either ID symbol or native raw symbol) also rejects. Other-account and unrelated-venue facts remain outside this report's scope.
- The final callback runs inside the private ingress, account state, execution state and read-only Cache boundary. It checks same reader generation/epoch, fully applied ingress, account/execution revisions, exact selected metadata and full serialized native HTTP/Cache instruments. `InstrumentAny` equality is deliberately avoided because it compares only IDs. TTL is sampled after the proof lock waits, and the total monotonic deadline is checked before report creation. No proof lock crosses an HTTP await.
- Native instrument checks bind exact selected ID/raw coin, venue, crypto-perpetual type, native quantity precision/increment, USD quote, USDC settlement and non-inverse convention. Native account equity/used/free must roundtrip exactly through USDC Money precision.
- Every selected verified ID gets a native Flat `PositionStatusReport` with exact native zero quantity precision and actual complete-clearinghouse source timestamp. Initialization uses actual local receipt time. The report explicitly sets `lookback_start` to the actual local startup account verification start and `reports_complete=false`. Empty orders/fills come from successful explicit array observations plus fresh empty durable origin. This is not all-history or all-venue completeness and never claims generic cold cache restoration.
- Any error or total timeout invalidates execution recovery/new-risk readiness while preserving durable facts, reservations, journal contents and debt.

## Limitations

The remote requests are non-atomic. This boundary fences local source identity, revision, metadata, receipt freshness and queued ingress; it does not claim atomic remote financial state. Any nonempty recent history is rejected even when economically harmless or belonging to a different DEX. A failed attempt closes new risk until normal explicit recovery succeeds again. Startup requires selected native instruments already present in both the normal HTTP instrument cache and engine Cache. It intentionally rejects any complete clearinghouse observation containing position rows, including zero-size retained rows, rather than extending this minimal fresh-empty contract.

Source SHA-256 and capture UTC are recorded in `io-startup-implementation-source.json`. This handoff describes authored source, not an independently reviewed or tested acceptance result.
